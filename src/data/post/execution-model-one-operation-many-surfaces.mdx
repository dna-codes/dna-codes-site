A team ships a working REST API for paying invoices. Product asks for an MCP server so an agent can do the same thing. Someone draws the ticket, opens the docs from memory, and writes a tool description by hand.

The tool says `amount` is optional. The endpoint has required it since March. An agent omits the field, gets a 400, and the failure gets logged as a hallucination. It was not. The model called what it was told exists.

That seam is the whole layer.

## The Execution Layer

[The Operational Model](/blog/operational-model-the-missing-abstraction/) names the work: actor, action, resource, plus the conditions under which the action applies. `Customer → Pay → Invoice`, only when `status = Issued`, only when `amount` is present and matches what is due.

**Execution is the layer where that operation becomes reachable.** Its key construct is the Interface: a REST endpoint, an MCP tool, a workflow step, a button. Each interface runs the operation. None of them should author it.

That is the same shape as the layer above. Operations has a primitive (the Operation). Execution has one too (the Interface). The layer is Execution. What you write down there is interfaces.

That is why this is a layer and not "good API hygiene." OpenAPI describes an endpoint. A JSON Schema describes a payload. An MCP tool definition describes a tool. Each is a faithful description of one interface. None of them sits upstream of the others. Contract-first development moved the artifact earlier without making it singular. Codegen from OpenAPI generates a client, not the operation's other faces.

## Four Interfaces, Four Drift Rates

The shape generalizes past MCP. The same `Pay Invoice` usually appears as:

| Interface      | What gets written by hand                    |
| -------------- | -------------------------------------------- |
| REST endpoint  | Path, body, status codes, error taxonomy     |
| MCP tool       | Name, description, parameter schema          |
| Workflow step  | Guards, retries, compensation                |
| UI command     | Affordance, validation, disabled state, copy |

Four interfaces. Four owners. Four calendars for when they get updated. They agree on the day they ship. They do not stay that way.

Agents make the cost visible faster than humans do. A person clicking a button and a person calling an endpoint still share tribal knowledge. An agent has only the tool description. The gap between what that description claims and what the operation enforces is not a documentation problem. It is the seam an agent probes first, often before QA does.

## Projection, Not Duplication

Projection means one operation definition, and every interface inherits its contract rather than restating it. Change a precondition once; every expression of it moves.

`status = Issued` becomes a 409 on the endpoint, a refusal in the tool's error contract, a guard on the workflow step, and a disabled button. `amount` required becomes a required body field, a required tool parameter, a step input, and a required form control. Same source. Four expressions. None of them authored separately.

Interfaces are not fully interchangeable. A UI needs affordances and copy. A queue consumer needs idempotency and retry semantics. An MCP tool needs a description written for a model's benefit. Projection settles the contract, not the presentation. Saying that out loud is what makes the rest credible.

## Prior Art, And The Gap

None of this invents contract modeling. OpenAPI, GraphQL SDL, protobuf, AsyncAPI, and JSON Schema are mature. MCP tool definitions are the newest face of the same idea. Smithy and AWS's model-first API generation already prove that one model can project many protocol interfaces, and that deserves explicit credit.

What those traditions mostly project from is a transport shape: paths, messages, payloads. They keep wire formats aligned. They do not carry the operation's preconditions, effects, and permission checks into every face that exposes it. The industry already accepts multi-interface projection. The missing move is projecting from the operation, not from the payload.

## The Execution Abstraction Layer

An abstraction layer is only real if you can say what it receives and what it produces.

**In, from the Operational Model: Projection.** The operation arrives with its contract intact: actor, action, resource, preconditions, effects. Execution does not renegotiate `status = Issued`. It projects that rule into each interface's idiom. The transformation is mechanical. A reviewer can check that the 409, the tool refusal, the workflow guard, and the disabled button all name the same condition.

**Out, to Code: Generation.** This is the handoff the industry has already built. Contract-first codegen from OpenAPI is unglamorous, which is the point. It is the first handoff on the way up the ladder that got engineered until it went boring. Use it as the existence proof for everything above it: once the interface contract is singular, generating the stubs, clients, and validators underneath it is ordinary work.

Knowing how an operation is reached is still not knowing how it is implemented. Execution hands Code a set of interfaces to fulfill. The next piece is about what happens when that contract, not the editor buffer, becomes where decisions stop living.
