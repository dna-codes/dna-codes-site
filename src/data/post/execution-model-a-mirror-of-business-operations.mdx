Years ago I worked with an architect who would not let "CRUD" into a design review. No Create Invoice button. No Update Loan endpoint. No InvoiceCreated event if what we meant was Issued. Every UI component, every API endpoint, every pub/sub message had to use business nouns and verbs: Issue Invoice, Close Loan, Escalate Claim. He was not being pedantic about naming. He was keeping the interface vocabulary identical to the work the business already had words for.

That discipline made our interfaces clean. More than that, it opened the door for a near-perfect mirror between the [operational model](/blog/operational-model-the-missing-abstraction) and the execution model: the same actor, action, and resource on both sides of the glass.

## The Execution Layer

**The Execution Model is where operational work becomes usable, with composable interfaces that faithfully reflect the underlying operational model.** Its construct is the Interface: a button, a form, a REST endpoint, a workflow step, an MCP tool. Each interface runs an operation. None of them should redefine it.

If the mirror is faithful, every surface agrees on preconditions, effects, and errors because they read from one operation. If it is not, you do not have an Execution Model. You have four interfaces that happen to share a name, often dressed in CRUD because that was the template in the scaffold.

## Interfaces for Operations

[Agent-Native](https://agent-native.com) puts the action at the center: define a capability once, and the agent, UI, HTTP clients, and integrations all call the same code. That is the right paradigm for Execution. Business operations need more than a bare action (actor, resource, conditions, workflows), but agent-native architecture is how interfaces should attach. The operation is what they attach to.

## Interfaces for Workflows

Operations compose. A customer submitting an order is not one interface. It is a workflow: validate on the frontend, submit through an API that validates again, create the order, send a confirmation email, and route to the confirmation page. Each step is still an operation with a noun and a verb. The actor, often the system, sits beside it.

## Why the Mirror Matters

Agents make a cracked mirror expensive faster than humans do. A person clicking a button and a person calling an endpoint still share tribal knowledge. An agent has only the tool description. When that description says `amount` is optional and the endpoint has required it since March, the agent omits the field, gets a 400, and the failure gets logged as a hallucination. It was not. The model called what it was told exists.

The industry already knows how to keep wire formats aligned. OpenAPI, GraphQL SDL, protobuf, AsyncAPI, and JSON Schema are mature. MCP tool definitions are the newest face of the same idea. Smithy and model-first API generation already prove that one model can project many protocol interfaces.

What those traditions mostly project from is a transport shape: paths, messages, payloads. They keep endpoints consistent with clients. They do not carry the operation's preconditions, effects, and permission checks into every face that exposes it. Multi-interface projection is accepted. The missing move is projecting from the business operation, not from the payload.

## The Execution Abstraction Layer

An abstraction layer is only real if you can say what it receives and what it produces.

**In, from the Operational Model: Projection.** The operation arrives with its contract intact: actor, action, resource, preconditions, effects. Execution does not renegotiate `status = Issued`. It projects that rule into each interface's idiom. The transformation is mechanical. A reviewer can check that the 409, the tool refusal, the workflow guard, and the disabled button all name the same condition.

**Out, to Code: Generation.** This is the handoff the industry has already built. Contract-first codegen from OpenAPI is unglamorous, which is the point. Once the interface contract is singular, generating the stubs, clients, and validators underneath it is ordinary work.

Knowing how an operation is reached is still not knowing how it is implemented. Execution hands Code a set of interfaces to fulfill. The next piece is about what happens when that contract, not the editor buffer, becomes where decisions stop living.
